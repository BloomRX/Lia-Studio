**Atualizado em 07/11/2026.** Escopo: branch `arena/01a0f4ab-lia-gamedev`, sandbox Linux sem engine, Agent Runtime, instalador Windows ou credenciais reais. O Dev escolheu concluir o produto **por marcos**: testar no sandbox o que é possível e reservar os testes com agente/engine/Windows para sua máquina. Prevalecem `docs/BRAND-STANDARDS.md`, `docs/AI-PROVIDERS-FREE-FIRST.md`, `docs/DECISOES-PENDENTES-INTEGRACOES.md` e gates atuais. Acesso pago, instalações, envio de dados e troca de branch exigem autorização específica.

## Critério de completude

O Studio só é *completo para um fluxo declarado* quando uma pessoa consegue preparar um jogo, dividir tarefas, executar com supervisão, importar/rodar na engine, testar e revisar gameplay, corrigir, produzir build e entregar no Windows com evidências reais. Cada fase conserva dados existentes e pode funcionar com artefatos manuais sem Forge. Um teste mock só valida o contrato offline; código presente não comprova operação em engine, gameplay, cofre Windows, instalação ou provedor remoto.

## Ordem e decisões para o próximo marco

1. **Hoje no sandbox:** manter a suíte `python verify_alpha.py --part N` **separada, uma parte por chamada**; agregar regressões para cada contrato novo. O marco 1 só lê descritores: não cria arquivo de estado, Session, QA ou autorização implícita. O teste UI é Node sob mock de HTTP; nenhum editor foi aberto.
2. **Antes do adapter executável:** Dev escolhe a primeira engine e sua versão, informa onde está o projeto do jogo (dentro ou fora da pasta de metadados Studio), define operações permitidas, tempo, isolamento, efeitos colaterais, logs e método de cancelamento. Projetos fora da pasta atual exigem seleção/autorização explícita e nova defesa de paths; não reutilizar um `path` vindo do cliente como comando. Não escolher engine nem interpretar metadados como instrução de build automaticamente.
3. **Antes do Runtime:** definir transporte real, capacidade mínima, prova de isolamento, limite de gasto por tarefa/tentativas e política de segredo/retenção. Testar falha, recusa, cancelamento e retomada antes de permitir execução. Não reclassificar a simulação existente como Session real.
4. **No Windows do Dev, depois:** confirmar binário/versão e projeto, executar engine e agente com dados descartáveis/consentidos, capturar saída e testar import, jogo e build. Testar empacotamento e instalação separadamente. Sem esses resultados, manter `NOT-TESTED`/`BLOCKED` nos relatórios, mesmo que a suíte Linux passe.

**Regra de progressão:** terminar cada marco com critérios de aceite, testes reproduzíveis e lista de pendências. Não apagar bloqueio por pressão de calendário ou por conclusão de documentação; uma conclusão verdadeira exige implementação e evidência na plataforma indicada.
